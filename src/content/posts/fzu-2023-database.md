    1. 视图<strong>不一定</strong>可以像基本表一样更新，要可更新视图（如行列子集视图）（不可更新：无法消解成基本表，不允许更新：用户不允许，如定义有GROUP BY的视图）

        1. 安全保护

3. 为什么关系中的元组没有先后顺序

    1. 由于关系定义为元组的集合，而集合中的元素是没有顺序的，因此关系中的元组也就没有先后的顺序。这样既能减少逻辑排序，又便于在关系数据库 中引进集合论的理论。

    2. 更改基本表

        ```sql
        ALTER TABLE <表名>
        [ADD [COLUMN] <新列名> <数据类型> [完整性约束] ]

        [DROP [COLUMN] <列名> [CASCADE|RESTRICT]]
        ```

    3. 删除基本表


### 第四章 数据库安全性

1. 安全等级划分

    1. 从低到高：D，C1，C2，B1，B2，B3，A1

    2. C1、C2可以进行DAC，B1可以进行MAC，B2可以DAC\+MAC

    3. DAC：自主存取控制，利用权限的授予和收回

    4. MAC：强制存取控制，利用密级和许可证机制

    5. <strong>实现MAC的前提是实现DAC</strong>，都是安全检查的部分

        1. 在DAC和MAC共同构成的数据库管理系统的安全机制

        2. 先进行DAC检查

        3. 只有通过DAC检查，再进行MAC检查

        4. 只有通过MAC检查的数据对象，方可存取

2. 数据库安全性控制：一级一级设置，从外到内

    1. <strong>用户标识和身份鉴别</strong>（用户层面）

    2. 数据库安全保护（数据库管理系统）

    3. 操作系统安全保护（操作系统）

    4. 数据密码存储（数据库）

3. 自主存取控制DAC（指令不用看）

    1. 创建角色

        1. 角色是权限的集合

        2. 特殊角色：public，默认所有用户都是public，不可指派不可删除，自带

        ```sql
        CREATE ROLE U1;
        ```

    2. 授予权限

        1. 授予者是数据管理员、数据库对象的创建者、拥有该权限的用户

        2. 不能循环授权

        ```sql
        GRANT UPDATE(Sno), SELECT     # GRANT ALL PRIVILEGES 授予所有权限
        ON TABLE Student, SC
        TO U4, U5
        WITH GRANT OPTION;            # 可以转授
        ```

    3. 收回权限

        ```sql
        REVOKE SELECT
        ON TABLE SC
        FROM U4 [CASCADE|RESTRICT];    # CASCADE 收回所有转授的权限，默认RESTRICT
        ```

    4. 授予角色

        1. 授予者是角色的创建者或者在这个角色上的ADMIN OPTION权限者

        ```sql
        GRANT U1, U2
        TO U3, U4
        WITH ADMIN OPTION;            # 可以转授
        ```

4. 强制存取控制MAC

    1. 全部实体分为主体和客体两类

        1. 主体是系统中的活动实体

        2. 课体是系统中的被动实体，受主体操纵

    2. 敏感度标记

        1. 绝密TS（Top Secret）

        2. 机密S（Secret）

        3. 可信C（Confidential）

        4. 公开P（Public）

        5. TS\>=S\>=C\>=P

    3. 主体的敏感度标记称为许可证级别

    4. 客体的敏感度标记称为密级

    5. 强制存取控制规则

        1. 许可证级别\>=密级，主体可读

        2. 许可证级别\<=密级，主体可写

        3. 禁止高许可证级别的主体更新低密级的数据对象，从而防止敏感数据泄露（高许可证级别的主体知道高密级的信息，可能会泄露）

5. 视图机制

    1. 把保密的数据对无权存取这些数据的用户隐藏起来，提供一定程度的安全保护

    2. 视图机制和授权机制结合

        ```sql
        # 建立视图
        CREATE VIEW CS_Student
        AS
        SELECT * FROM Student
        WHERE Smajor='计科'
        WITH CHECK OPTION;
        
        # 授予权限
        GRANT SELECT ON CS_Student 
        TO WangPing;
        
        GRANT ALLPRIVILIGES ON CS_Student
        TO ZhangMing;
        ```

6. 审计

    1. 启用一个审计日志，把用户所有操作记录放入审计日志

    2. 审计员利用审计日志监控数据库的各种行为

    3. 审计事件

        1. 服务器事件

        2. 系统权限

        3. 语句事件

        4. 模式对象事件

    4. 分类

        1. 用户级审计

        2. 系统级审计

    5. AUDIT语句，设置审计功能

    6. NOAUDIT语句，取消审计功能

7. 数据加密

    1. 防止数据库中的数据在存储和传输中失密的手段

    2. 基本思想：将明文变换为密文

    3. 加密方法：替换方法，置换方法，混合方法

### 第五章 数据库完整性

1. 实体完整性

    1. 用主码实现

    2. 要求唯一\+非空，否则拒绝插入或修改

    3. 自动建立索引

2. 参照的完整性

    1. 用外码实现：

    2. 要求外码只能取被参照关系的主码的值或NULL

    3. 四种破坏参照完整性的情况（默认都是拒绝）

        1. 在参照关系中插入新元组，在被参照关系的主码中找不到与之对应的，<strong>拒绝插入</strong>

        2. 修改参照关系的一个元组，在被参照关系的主码中找不到与之对应的，<strong>拒绝修改</strong>

        3. 删除被参照关系的一个元组，使得参照关系的某些元组无法有对应的被参照关系，<strong>拒绝删除/级联删除/设置为空</strong>

        4. 修改被参照关系的一个元组，使得参照关系的某些元组无法有对应的被参照关系，<strong>拒绝修改/级联修改/设置为空</strong>

    4. 显式说明违约处理

        ```sql
        CREATE TABLE SC(
        Sno CHAR(8), 
        Cno CHAR(5), 
        PRIMARY KEY (Sno, Cno), 
        FOREIGN KEY (Sno) REFERENCES Student(Sno)
        ON DELETE CASCADE        # 删除Student(Sno)时，如果破坏参照完整性，级联删除相应的值
        ON UPDATE NO ACTION );   # 修改Student(Sno)时，如果破坏参照完整性，拒绝修改
        ```

3. 用户定义的完整性

    1. 属性上的约束，列级

        1. 列值非空

            ```sql

            ```

        2. 列值唯一


        3. 检查满足条件表达式

4. 完整性约束命名，便于修改

    1. 定义约束

    2. 更改约束


5. 触发器

    1. 定义：<strong>事件\-条件\-动作</strong>规则

        1. 当特定的系统<strong>事件发生</strong>时，对规则的<strong>条件</strong>进行<strong>检查</strong>

        2. 如果条件成立则<strong>执行</strong>规则中的<strong>动作</strong>，否则不执行该动作

        3. 动作可以很复杂，通常是一段SQL存储过程

    2. CREATE TRIGGER 格式

        ```sql
        CREATE TRIGGER <触发器名>            # 同一模式下，触发器名唯一
        {BEFORE|AFTER} <触发事件> ON <表名>   # 只能定义在表上，视图不行
                                             # 触发事件可以是INSERT、UPDATE、DELETE或者这些的组合
                                             # 或UPDATE OF<触发列> 指明修改哪一列
                                             # BEFORE：在触发事件操作的执行前激活触发器
                                             # AFTER：在触发事件操作的执行后激活触发器
        REFERENCING NEW|OLD AS <变量>        # OLD表示旧值，NEW表示新值(语句级触发器不能用)
        FOR EACH {ROW|STATEMENT}
                                             # 行级触发器（FOR EACH ROW）：语句影响几行触发几次，一行触发一次
                                             # 语句级触发器（FOR EACH STATEMENT）：一个语句触发一次
        [WHEN <触发条件>]
        BEGIN
        <触发动作体>                          # PL/SQL过程块，如果执行失败，激活触发器的事件也终止执行
        END;
        ```

    给个例子

    ```sql
    # 行级触发器
    CREATE TRIGGER SC_T
    AFTER UPDATE ON SC
    REFERENCING                         # 引用的是旧元组和新元组
        OLD AS OldTuple
        NEW AS NewTuple
    FOR EACH ROW
    WHEN (NewTuple.Grade >= 1.1 * OldTuple.Grade)
    BEGIN
        INSERT INTO SC_U(Sno, Cno, OldGrade, NewGrade)
        VALUES (OldTuple.Sno, OldTuple.Cno, OldTuple.Grade, NewTuple.Grade)
    END;
    
    # 语句级触发器
    CREATE TRIGGER Student_count
    AFTER INSERT ON Student
    REFERENCING NEWTABLE AS Delta       # 语句级触发器只能直接引用旧表和新表（OLDTABLE和NEWTABLE）
    BEGIN 
        INSERT INTO StudentInserting(Numbers)
        SELECT COUNT(*) FROM Delta
    END;
    
    # 带条件语句的
    CREATE TRIGGER Update_Sal
    BEFORE UPDATE ON Teacher
    REFERENCING NEW AS newTuple
    FOR EACH ROW
    BEGIN
        IF(newTuple.job='Professor') AND (newTuple.sal<4000)
        THEN newTuple.sal = 4000
        END IF;
    END;
    ```

    3. 执行触发器：

        1. 先执行BEFORE触发器

        2. 再执行激活触发器的SQL语句

        3. 最后执行AFTER触发器

    4. 删除触发器

        1. 只有相应权限的用户才能删除，触发器必须已创建

        ```sql
        DROP TRIGGER <触发器名> ON <表名>;
        ```

### 第六章

1. 关系数据库的逻辑设计

    1. 针对具体问题，应该构造几个关系，每个关系由哪些属性组成

    2. 数据库逻辑设计的工具——关系数据库规范理论

    3. 存在的问题

        1. 数据冗余度大，浪费存储空间

        2. 更新异常：更新时，维护数据完整性代价大

        3. 插入异常：无法插入数据

        4. 删除异常：不该删除的数据也删除了

    4. 原因：存在模式中的某些<strong>数据依赖</strong>引起的

    5. 解决方法：用规范化理论搞糟关系模式，<strong>消除不合适的数据依赖</strong>

2. <strong>nNF</strong>

    1. <strong>1NF：</strong>所有属性都是不可分的数据项

    2. <strong>2NF：</strong>不存在非主属性对码的部分函数依赖

    3. <strong>3NF：</strong>不存在非主属性对码的传递函数依赖

    4. <strong>BCNF：</strong>不存在主属性对码的部分和传递函数依赖

    5. <strong>4NF：</strong>消除非平凡且非函数依赖的多值依赖

    6. <strong>5NF：</strong>消除连接依赖

    7. <strong>5NF ⊇ 4NF ⊇ BCNF ⊇ 3NF ⊇ 2NF ⊇ 1NF</strong>

3. 数据依赖

    1. 是什么

        1. 属性间的相互关联，通过属性间值的相等与否描述

        2. 体现数据之间的相互关联

        3. 数据库模式设计的关键

    2. 类型

        1. 函数依赖，FD

            1. 定义：Y=F（X）的映射，记作，X→Y

            2. 平凡与非平凡的函数依赖

                1. 平凡的函数依赖：X→Y，但X⊇Y，否则非平凡

                2. 默认讨论非平凡的函数依赖

            3. 部分和完全的函数依赖

                1. 完全函数依赖：X→Y，对于X的任意一个真子集X'（属性的真子集）,X'→Y不成立，在X→Y箭头上标F

                2. 部分函数依赖：\~\(X→Y\)，与上面的定义相反，在X→Y的箭头上标P

            4. 传递函数依赖

                1. 若X→Y（不满足X←→Y），Y→Z，则称Z对X的传递函数依赖，在X→Z的箭头上标T

                2. 满足X←→Y的话（X→Y同时Y→X），Z直接依赖于X，即X→Z

        2. 多值依赖，MVD

            1. Teaching（C，T，B）：对于C的每个值，都有一组T的值对应，且无论B取何值，T与B不相关。

            2. T多值依赖于C，记C→→T

        3. 包含依赖

4. 推理规则：

    1. <strong>自反律：</strong>如果U⊇X⊇Y，则X→Y成立（得到一个平凡的函数依赖）

    2. <strong>增广律：</strong>X→Y为F所蕴含，则XZ→YZ也蕴含

    3. <strong>传递律：</strong>如果X→Y，Y→Z为F所蕴含，则X→Z也为F所蕴含

    4. 导出规则

        1. <strong>合并规则：</strong>由X→Y，X→Z，有X→YZ

        2. <strong>伪传递规则：</strong>X→Y，WY→Z，有XW→Z

        3. <strong>分解规则：</strong>由X→Y和Y⊇Z，有X→Z

        4. 引理：X→A1A2\.\.\.Ak的充分必要条件是X→Ai均成立（i=1,2,\.\.\.,k）

    5. 函数依赖闭包：F所逻辑蕴含的函数依赖的全体，记作F^\+

    6. 属性关于F的闭包：从闭包中选出属性能推出的属性的全体，X\_F^\+=\{A\|X→A∈F^\+\}

5. <strong>求闭包算法</strong>

    1. 输入X，F

    2. 输出X\_F^\+

    3. 步骤

        1. 令X（0）=X ，i=0

        2. 求从F中把所有能推导的属性集B=\{A\|V→W∈F ＆ V∈X（i）＆ A∈W\}

        3. X（i\+1）=X（i）∪B

        4. 如果X（i\+1）=X（i）或X（i\+1）=U，终止，否则返回ii

6. <strong>候选码求解</strong>

    1. 四类属性

        1. L类，只出现左侧

        2. R类，只出现右侧

        3. LR类，两侧都出现

        4. N类，两侧都不出现

    2. L类属性必为R的任一候选码的成员

    3. R类属性必不在任何候选码中

    4. N类属性必在R的所有候选码中

7. 函数依赖集等价

    1. F^\+=G^\+，则F与G等价

    2. 判定方法：F\+⊇G且G\+⊇F

    3. 判断方法：不能有以下三种

        1. 形如X→YZ的

        2. 如ABC→D，尝试去掉A，如果BC闭包内有D，或BC闭包等价于ABC闭包，则A冗余

        3. F中的某个函数依赖能由其他函数依赖导出

8. <strong>极小化处理，对F作三步处理</strong>

    1. 右边单属性化，如果有形如X→YZ的，拆解为X→Y和X→Z

    2. 冗余判断

        1. F中所有函数依赖不能由其他函数依赖导出

        2. 如果存在就删除

    3. 左边既约化，F中X→A，X有真子集Z使得F\-\{X→A\}∪\{Z→A\}与F等价，左边不允许冗余

        1. 做法：如ABC→D，尝试去掉A，如果BC闭包内有D，或BC闭包等价于ABC闭包，则A冗余，删去A

9. <strong>保持函数依赖的模式分解</strong>

    1. 定义：把一个关系模式分解成若干子关系模式，且能够保持函数依赖

    2. <strong>3NF的保持函数依赖的分解</strong>

        1. 先求F的最小依赖集Fm

        2. 将N类属性单独构成一个关系模式，U=U\-N

        3. 将剩余的左部相同的函数依赖合并成新关系

    3. 判断：F的闭包投影到子模式后和F的闭包等价，故模式分解保持函数依赖

10. <strong>无损连接的模式分解</strong>

    1. 定义：把一个关系模式分解成若干子关系模式，可以通过自然连接来恢复原始关系

    2. 判断无损连接算法：

        1. 先建立一个k行n列的表，k是子关系数，n是属性数。如果属性Aj属于关系Ui，在i行j列处填aj，否则填bij

        2. 对每个FDi（X→A）做

            1. 在所有行中找X所对应的列的具有相同符号的行

            2. 找到对应A的列，如果这些行中都有ai，则全部填成ai，否则填为b\_min\(i\)，j

        3. 对每个FD都做一次后，称为一次扫描，如果扫描前后无变化，认为有损分解

        4. 如果某次扫描后，某一列为a1，a2，\.\.\.，an，则其为无损分解

11. <strong>既无损连接又保持函数依赖的模式分解</strong>

    1. <strong>最高分解到3NF</strong>

    2. 先从<strong>3NF的保持函数依赖的分解</strong>开始，加入一个新的子模式，由<strong>原模式的码X</strong>组成：U∪\{R\*\(X, F\_X\)\}

    3. 如果某个子模式Ui⊇X，则把这个R\*关系删去

    4. 如果某个子模式X⊇Ui，则把这个子模式删去

12. <strong>转换为BCNF的无损连接分解</strong>

    1. 先从<strong>3NF的保持函数依赖的分解</strong>开始

    2. 检查每个子模式，如果不是BCNF，必有X→A∈Fi\+（A不属于X），且X非Ri的码（部分主属性），拆解为Ui1=XA，Ui2=Ui\-A

    3. 直到每个子模式都是BCNF

13. <strong>达到4NF的无损连接分解</strong>

    1. 先从<strong>BCNF的保持函数依赖的分解</strong>开始

    2. 检查每个子模式，如果不是4NF，就拆解得到4NF的子模式，直到所有子模式都是4NF

### 第十一章 数据库恢复技术

1. 事务的基本概念

    1. <strong>用户定义的</strong>一个<strong>操作序列</strong>，要么全做要么全不做，是<strong>不可分割</strong>的工作单位

    2. 特性

        1. <strong>原子性A：</strong>要么全部提交要么全部回滚                    <strong>基础</strong>

        2. <strong>一致性C：</strong>从一个合法状态转换为另一个合法状态   <strong>约束条件</strong>

        3. <strong>隔离性I：</strong>一个事务的执行不被另一个事务干扰    <strong>手段</strong>

        4. <strong>持久性D：</strong>修改永久生效                                     <strong>目的</strong>

    3. 事务以 <strong>BEGIN TRANSACTION</strong> 开始，以 <strong>COMMIT（提交）</strong> 或 <strong>ROLLBACK（回滚）</strong> 返回

2. 故障种类

    1. 故障不可避免

    2. 故障意味着

        1. 事务<strong>没有达到预期的终点</strong>（COMMIT或ROLLBACK）

        2. 数据库可能处于<strong>不正确</strong>状态

            1. 部分尚未完成的事务的结果可能已送入数据库，导致数据库不正确

    3. 事务内部故障：

        1. 预期的：代码bug

        2. 非预期的：运算溢出

        3. 解决方法：UNDO

    4. 系统故障：软故障，造成系统停止运作的任何事件，系统要重新启动，不影响数据库

        1. 恢复：系统重启时，启动恢复程序

            - UNDO未完成的事务，REDO已提交的事务

    5. 介质故障：硬故障，外存故障

        - 成因：

            - 磁盘损坏

            - 磁头碰撞

            - 瞬时强磁场感染

            - 破坏硬盘数据的计算机病毒

3. 转储

    1. 数据库管理员定期地将<strong>整个数据库</strong>复制到存储介质上保存起来的过程

    2. 转储方式

        1. 动态和静态

            1. <strong>动态转储：</strong>转储操作和用户事务并行，允许用户进行存取或修改

                1. 必须建立日志文件，才能恢复数据库

            2. <strong>静态转储：</strong>系统中无运行事务时转储

                1. 可以建立日志文件，对已完成的重做，未完成的撤销

        2. 海量和增量

            1. <strong>海量转储：</strong>每次转储更新全部数据库

            2. <strong>增量转储：</strong>只转储上一次转储后更新过的数据

4. 日志文件

    1. 日志文件是用来记录事务对数据库的更新操作的文件

    2. 以<strong>记录</strong>为单位的日志文件

        1. 事务标识（哪个事务）

        2. 操作类型（插入、删除或修改）

        3. 操作对象

        4. 更新前数据的旧值（插入操作时为空）

        5. 更新后数据的新值（删除操作时为空）

    3. 以<strong>数据块</strong>为单位的日志文件

        1. 事务标识

        2. 被更新的数据块

    4. 用途

        1. 进行<strong>事务故障</strong>恢复

        2. 进行<strong>系统故障</strong>恢复

        3. 协助后备副本进行<strong>介质故障</strong>恢复

    5. 原则

        1. 登记的次序严格按并发事务执行时间的次序（但是和时间戳没关系）

        2. 必须先写日志文件，再写数据库（如果先写数据库，会导致操作没被写进日志文件；先写日志文件，出了故障可以UNDO）

5. 恢复策略

    1. REDO已完成的事务

    2. UNDO未完成的事务

    3. 事务故障恢复

        1. 恢复方法

            1. UNDO此事务对数据库的修改

        2. 恢复步骤

            1. <strong>反向扫描</strong>日志文件，查找该事务的更新操作

            2. 对该事务的更新执行逆操作，把更新前的值写回数据库

    4. 系统故障恢复

        1. 造成不一致的原因

            1. 未完成的事务的更新可能已经写入数据库

            2. 已提交的事务的更新可能还停留在缓冲区，未写入数据库

        2. 恢复步骤

            1. <strong>正向扫描</strong>日志文件，构建事务队列

                1. <strong>重做队列：</strong>故障发生时已提交的事务

                2. <strong>撤销队列：</strong>故障发生时未完成的事务

            2. 先对<strong>撤销队列</strong>的事务做撤销处理

                1. <strong>反向扫描</strong>日志文件，对撤销事务的更新操作执行逆操作

                2. 把更新前的数据写回

            3. 再对<strong>重做队列</strong>的事务做重做处理

                1. <strong>正向扫描</strong>日志文件，对每个重做事务的重新执行登记的操作

                2. 把更新后的数据写回

    5. 介质故障恢复

        1. 步骤

            1. 装入最新的后备数据库副本，使数据库恢复到最近一次转储时一致的状态

                1. 静态转储装入就是一致的

                2. 动态转储需要利用系统故障恢复的方法

            2. 装入有关的日志文件副本

                1. 先扫描日志文件，找出已提交的事务的标识，计入重做队列

                2. <strong>正向扫描</strong>日志文件，对重做队列进行重做处理

        2. 需要DBA的介入

            1. 重装数据库副本和日志文件的副本

            2. 执行系统提供的恢复命令

    6. 检查点记录

        1. 内容

            1. 建立检查点时刻所有正在执行的事务清单

            2. 这些事务最近一个日志记录的地址

        2. 重新开始文件

            1. 记录各个检查点记录在日志文件的<strong>位置</strong>

        3. 恢复策略

            1. 定期或不定期的建立检查点

                1. 定期：预定的时间间隔

                2. 不定期：按照某种规则

            2. 检查点前完成：不需要重做

            3. 检查点\~故障前完成：重做

            4. 故障发生时未完成：撤销

        4. 步骤

            1. 由重新开始文件找到最后一个检查点记录在日志文件中的地址，找到最后一个检查点记录

            2. 由检查点记录找到正在执行的事务清单ACTIVE\-LIST

                1. 建立REDO\-LIST和UNDO\-LIST

                2. ACTIVE\-LIST存入UNDO\-LIST，REDO\-LIST为空

            3. 从检查点开始<strong>正向扫描</strong>日志文件，直到日志结束

                1. 如有新开始的事务Ti，暂时放入UNDO\-LIST

                2. 如有提交的事务Tj，把事务从UNDO\-LIST移到REDO\-LIST

            4. 对UNDO\-LIST的事务做UNDO，REDO\-LIST的事务做REDO

        5. 解决了以下问题

            1. 搜索整个日志将耗费大量时间

            2. 需要很多REDO序列，实际上已经将更新操作的结果写到据库中了，而恢复子系统重新执行了这个操作，浪费大量时间

6. 数据库镜像

    1. 自动把数据库复制到另一个磁盘上

    2. 自动保证镜像数据和主数据一致性

        1. 主数据库更新后，自动复制到镜像

    3. 出现介质故障后

        1. 镜像磁盘继续提供使用

        2. DBMS自动利用镜像数据恢复数据库

        3. 不需要关闭系统和重装数据库副本

    4. 无故障时可以用于<strong>并发操作</strong>，读写分离，提高并发度

    5. 只对关键数据和日志文件镜像——频繁复制数据会降低系统的运行效率

7. 建立冗余数据最常用的方法是

    1. 数据转储

    2. 建立日志文件

### 第十二章 并发控制

1. 为了保证<strong>隔离性</strong>和<strong>一致性</strong>，要DBMS要进行正确的调度

2. 并发操作带来的不一致性（破坏事物的隔离性）

    *用例说明：事务T1，事务T2，数据D*

    - （丢失修改）脏写：两个事务同时对一个D写，导致操作被覆盖

    - （读”脏“数据）脏读：T1修改D，T2读取D，而后T1撤销更改，导致T2读到脏数据

    - 不可重复读：T1读取D后被T2更新，导致T1无法复现

    - 幻读：T1读取D后，被T2插入/删除，导致T1无法复现

    严重性排序：脏写＞脏读＞不可重复读＞幻读

3. 并发控制的主要技术

    - 封锁：事务在操作之前申请对数据加锁，加锁期间其他事务不能更新或读取，用完后释放锁

    - 时间戳：

        - 给每个事务该一个时标，即事务的开始时间

        - 每个事务有唯一的时间戳，按照时间戳解决冲突

        - 如果发生冲突，回滚较早时间戳的事务，赋予新的时间戳，重新运行

    - 乐观方法

        - 认为事务执行时很少发生冲突，不做特殊管制

        - 自由执行，提交前做特殊性检查

        - 如果出现冲突并影响可串行性，拒绝并回滚

    - 多版本并行控制

        - 维护多个版本信息实现高效并发控制

        - 根据版本的时间戳和事务的时间戳来控制回滚和覆盖

4. 四个隔离级别

    - <strong>读未提交：</strong>所有事务都能看到其他未提交事务的执行结果

        - 只能解决脏写

    - <strong>读已提交：</strong>一个事务只能看见已提交事务所做的改变

        - 解决脏写、脏读

    - <strong>可重复读：</strong>事务A在读数据后事务B进行修改并提交，事务A再次读取数据读到的仍然是原来的内容

        - 解决脏写、脏读、不可重复读

    - <strong>可串行化：</strong>事务持续期间禁止其他事务进行插入、更新和删除。

        - 解决脏写、脏读、不可重复读、幻读

        - 效率低下

5. 加锁类型

    1. 排它型锁（X锁）：只允许本身读取和修改

    2. 共享型锁（S锁）：事务本身只读不写，其他事务能上S锁、不能上X锁

    3. 意向锁

        1. 定义：对任一结点加锁，必对其上层结点加意向锁

        2. 意向共享型锁（IS锁）：它的后裔结点加S锁

        3. 意向排它型锁（IX锁）：他的后裔结点加X锁

        4. 共享意向排它型锁（SIX锁）：先加S锁再加IX锁

    4. 锁的强度：X＞SIX＞S=IX＞IS

        - 一个事务在申请封锁时用强锁换弱锁是安全的，反之不然

7. 三级封锁协议

    1. 约定一些规则

        1. 何时申请X锁或S锁

        2. 持锁时间

        3. 何时释放

    2. 一级封锁协议：事务只有在修改之前上X锁，事务结束释放

        1. 正常结束COMMIT

        2. 非正常结束ROLLBACK

        3. 读未提交级别

    3. 二级封锁协议：在一级的基础上，事务在读取数据之前上S锁，读取后释放

        1. 读已提交级别

    4. 三级封锁协议：在一级的基础上，事务在读取数据之前上S锁，事务结束后释放

        1. 可重复读级别

8. 活锁

    1. 某事务在申请封锁时等待，系统调度不断把封锁批准给晚来的事务，造成该事务一直等待

    2. 如何避免活锁（饥饿）：<strong>先来先服务</strong>策略

9. 死锁预防

    1. 一次封锁法：把需要的数据全部枷锁

    2. 顺序封锁法：规定一个封锁顺序，所有事务按序封锁

10. 死锁诊断和预防

    1. 死锁诊断

        1. 超时法：超时就发生死锁（有可能误判）

        2. 事务等待图法：用事务等待图，如果出现回路则死锁

11. <strong>调度可串行化</strong>

    1. 多个事务的并发执行是正确的，当且仅当其结果与按<strong>某一次序</strong>串行的执行这些事务的结果相同

    2. 可串行性

        1. 并发事务正确调度的准则

        2. 只有可串行化才是正确的

    3. <strong>判定：优先图</strong>

        1. 如何建图：以下条件之一成立，在E中加入Ti→Tj

            1. Ri（X）在Wj（X）前

            2. Wi（X）在Rj（X）前

            3. Wi（X）在Wj（X）前

        2. 如何判定：优先图中无回路，可串行化

        3. 寻找等价调度：拓扑排序

12. 冲突可串行化

    1. 比可串行化更严苛，要求并发操作序列需要进行交换，得到可串行序列，才能说明是冲突可串行化

    2. 不能交换的动作

        1. 同一事务的两个操作

        2. 不同事务的冲突操作

            1. 不同事务对同一数据的读写顺序（一个读一个写）

            2. 不同事务对同一数据的写入顺序（都写）

13. 两段封锁协议

    1. 事务分为两个阶段

        1. 第一个阶段只获得封锁不释放锁

        2. 第二个阶段只释放锁不获得封锁

        3. 不一定要连续封锁或释放，只要能分成两个部分就行

    2. 遵守两段封锁协议是可串行化调度的充分条件

    3. 两段封锁协议不等于一次封锁法

    4. 两段封锁协议<strong>可能会引发死锁</strong>，而一次封锁法不会

14. 申请锁的多粒度封锁方法

    1. 封锁对象：逻辑单元、物理单元

        1. 封锁对象的大小称为封锁粒度

        2. 封锁粒度越大，开销越小，并发度小

        3. 封锁粒度越小，开销越大，并发度大

        4. 具有意向锁的多粒度封锁可以<strong>提高并发度、减少解锁和开锁的开销</strong>

    2. 多粒度树

        1. 性质

            1. 每个结点独立被加锁

            2. 一个结点被加锁意味着其后裔结点也被加同样的锁

            3. 两种方式：显式封锁和隐式封锁

                1. 显式：直接加到数据上

                2. 隐式：不独立加锁，依靠上级结点决定

                3. 效果一样

        2. 加锁时，检查封锁：

            1. 检查显式锁和隐式锁

            2. 检查该数据对象有无显式锁与本事务冲突

            3. 搜索上级结点有无显式锁与本事务的隐式锁冲突

            4. 搜索下级结点有无显式锁与本事务的隐式锁冲突

        3. 申请封锁时应<strong>自上而下</strong>进行

        4. 释放封锁时应<strong>自下而上</strong>进行

    3. 优势：同时考虑<strong>封锁开销和并发度</strong>两个因素，根据事务特点选取相应的并发度，减少加锁和解锁的开销
